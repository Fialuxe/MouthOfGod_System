## 2026-10-15 何が届いても受け取り、戻るのは頼まれた物だけ。届いた物の種類を知らせる（案）

**決めたこと**: フィールドは、何が届いても受け取る（`Receive`）。戻るのは、吹き出しで頼まれた物が届いたときだけ。届くたびに、何だったか（`Requested` = 頼まれた物 / `Own` = このフィールドの物だが頼まれていない / `Foreign` = よその物）を `Received` で知らせる。頼む順番は、フィールドごとに並び順かランダムかを選べる。

**理由**: 体験者は頼まれていない物も投げてくる。2 本目のにんじんで「やたらと豊作になる」、村に豚で「いびつな世界になる」のような反応や、採点（未定）を、あとから足せるようにするため。反応・採点の決まりは未定で、知らせを受けた側に足す（フィールドの仕組みは直さない）。

**採用しなかった案**
- 頼まれていなくても、このフィールドの物なら戻す: 何を頼むかで戻り方を決める、という形が崩れる（PR #251 の議論で、起こらないことにした）。
- 届いたかを「受け取った・受け取らなかった」の 2 つで知らせる（最初の `Delivered.Accepted`）: 豊作といびつな世界を区別できない。

## 2026-10-15 全部をつなぐ組み立て役（Bootstrap）は置かず、Core の置き場に自分で登録する（案）

**決めたこと**: 機能をまたいで使う「もの」（デバイス・フィールド）は、Core の置き場（`Devices`・`Fields`）に自分で登録し、使う側はそこから受け取る。全機能を参照する Bootstrap は置かない。置き場は「もの」にだけ作り、増やすのは「体験者がいまいるフィールド」「いまの場面」のように、機能をまたぐ「もの」が増えたときだけ。

**理由**: 山・海・草原・村を 4 人が別々に作り、最後に 1 つのシーンにまとめる。登録する形なら、作ったフィールドは置くだけで本編・チュートリアル・吹き出しにつながり、1 人ずつ自分のサンドボックスで試せる。どの機能も Core しか知らないので、密結合にならない。「Mock に自動で切り替わる」は、すでに `Devices` が満たしている。

**採用しなかった案**
- Bootstrap が組み立てる（#34 の案）: つながりを 1 ファイルで見渡せるが、機能を足すたびに全員が Bootstrap を直す（`GameManager` と同じ問題）。Bootstrap ができるまで、誰もつないで動かせない。
- 知らせの通り道（イベントバス、ScriptableObject のイベントチャンネル）: 結合は最も低いが、誰が出して誰が受けるかを追えない。`Open` の戻り値のような返事や、`Issued` と `Closed` が交互、のような順番の約束を守らせにくい。チャンネルを `.asset` にすると Git でぶつかりやすい。

## 2026-10-15 フィールドの戻り方は Hierarchy の並びで持ち、欲しい物を出す時は Game・Tutorial が決める（案）

**決めたこと**: フィールドの戻り方は、`Steps` の下に並べた `FieldStep`（欲しい物・困りごとが解ける人・消す物。子は済むと出る物）で持つ。順番は Hierarchy の並び順で、番号は持たない。いつ・どのフィールドに欲しい物を出すかは、Core の `IFieldRequests` 越しに、本編は Game、チュートリアルは Tutorial が決める。詳しくは [requests.md](requests.md)。

**理由**: 山・海・草原・村を別々の人が同時に作り、それでも 4 つが調和して動くようにするため。フィールドの担当は自分の Prefab だけを触り、時間や他のフィールドを考えない。出す順番と間隔は 1 か所で決めるので、ばらばらに動かない。段階を途中に挟む・並べ替えるのが Hierarchy の操作だけで済む。合わせ目は `IFieldRequests` 1 つなので、フィールドを独自の作りにしても本編にそのままつながる。

**採用しなかった案**
- 全体で 1 つの `RequestSet`（要求の並び）と、順に出す `RequestIssuer`（PR #251 の最初の形）: 4 人が同じアセットを触る。本編の「同時に最大 2 つ・20 秒で消える」を表せない。どの村人の上に出すか分からない。
- 段階を番号で持つ（#237 の `StageVisibility` の from〜until と `VillagerMood` の `calmFromStage`）: 途中に段階を挟むと後ろの番号を全部ずらす必要があり、ずらし忘れても気づけない。
- フィールドの中の順番を自由にする: 今は最初の未済のステップを出す。済んだかはステップごとに持つので、要ると分かったら `StepProgress.NextIndex` を変えるだけで済む。

## 2026-10-13 コードの型・データの置き場所・シーン・チュートリアルの引き継ぎ・密結合の検査

**なぜ必要だったか**
- M2 の全実装の土台 #30（Core の型とイベント）が、#41（型の名前とデータの置き場所）を待っていた。M1 が遅れていて、ここが詰まりの 1 つだった。
- 名前と置き場所がそろわないまま書き始めると、あとで全員が直す。複数人が同じファイルを触ると、順番待ちになる（`.unity` `.prefab` `.asset` は Git でマージできない）。
- 機能どうしが絡み合う（密結合）と、1 か所の変更が全体を壊し、作業が止まる。応募（10/30）までに、そうなってはいけない。

**何を考えたか**
- 食べ物と生物を別の型にするか → 違いは「データの中身」で表せるので、同じ型にした。
- ID を `enum` にするか → 食感や食べ物を足すたびに全機能が再コンパイルされ、素材担当が触れなくなる。文字列にした（重複は起動時にエラー）。
- データをどこに置くか → Prefab がすでに `Assets/Resources/Prefabs/` にあるので、データも `Assets/Resources/Data/` にそろえた。欠点は、`Resources/` の中身が全部ビルドに入ること。だから、置くものを「起動時に読むデータと Prefab」に絞った。
- チュートリアルどうしは互いを知らないが、データは引き継ぎたい → 引き継ぐものを「名前の付いた記録」にして、Core の `IProgress` を通して読み書きする案にした。T3 は T2 を見ず、記録の名前だけを見る。
- 密結合の防ぎ方 → 全機能に asmdef を強制するのは重い。まず、直接参照を PR の警告で知らせる軽い検査を入れた。

**どうなったか**
- 型は `Food`（`FoodDefinition` `FoodId` `FoodCatalog`）、`FieldId` `FieldDefinition`、`RequestSet`（2026-10-15 にやめた。上の記録）、`TutorialStep`、`TextureId`。ID は文字列。データは `Assets/Resources/Data/<種類>/`、1 件 = 1 アセット。→ [CONTRIBUTING「型の名前とデータの置き場所」](../CONTRIBUTING.md#型の名前とデータの置き場所)
- 実行用の共有シーンは `Assets/Scenes/Main.unity` の 1 つ。個人の確認用は `Assets/Scenes/Sandbox/`。
- 引き継ぎは `IProgress` の案（**案のまま。実装するときに確定する**）。記録の名前は [progress-keys.md](progress-keys.md) の 1 か所に書く。
- 機能が他の機能を直接参照すると、PR に警告が出る（`.github/scripts/check_coupling.py`、止めはしない）。

**採用しなかった案**
- チュートリアルごとに分岐する中央の進行クラス（`GameManager`）: 足すたびに共通ファイルを編集し、互いを壊す。
- チュートリアルどうしの直接参照: 片方を直すと、もう片方が壊れる。
- 全機能に asmdef を強制する: 新しい機能のたびに設定が要り、今の人数と時間には重い。

**見直すとき**: 警告が増えて、レビューで防げなくなったら、全機能に asmdef を置く。`Resources/` が重くなったら、置き方を見直す。`IProgress` は、最初の引き継ぎが必要になった実装で確定する。

**実装する人が把握すること**: [Assets/Scripts/README.md「実装する前に」](../Assets/Scripts/README.md#実装する前に役割ごとに知っておくこと)。

## 2026-10-09 共有シーンは 1 つにし、Scene Fusion で一緒に編集する

**決めたこと**: 村全体と全フィールドを 1 つの共有シーン（例: `Main`）に置き、シーンは分けない。複数人で編集するときは Scene Fusion を使う。約束は [architecture.md「シーンを 1 つにするときの約束」](architecture.md#シーンを-1-つにするときの約束)。

**理由**: シーンを分けると、加算ロードや位置合わせのつなぎ、サンドボックスで作ったものを他の人のシーンと合わせる手間がかかり、このチームには重い。複数人で同時に編集できる Scene Fusion の方が強い。

### 採用しなかった案: フィールドごとにシーンを分ける

**見直すとき**: Scene Fusion が使えなくなったとき（席が足りない、不安定、オブジェクト数の上限）。CONTRIBUTING「席が足りない・接続できない場合」とあわせて検討する。関連: #6、#20、#34、#43。

#### この案の利点（Scene Fusion があっても残るもの）
- 別々の時間に作業しても、保存するシーンファイルが別なのでぶつからない（Scene Fusion は同じ時間にセッションにいる時しか助けにならない）
- Scene Fusion の席（無料は 2 人）がない人も、自分のフィールドを編集できる
- Scene Fusion が不安定なときの逃げ道になる

#### この案のコスト
- 加算ロードと、実行時に村の基準へつなぐコード
- 複数シーンを同時に開いての編集、シーンをまたぐ参照ができない
- サンドボックスで作ったものを、他の人のシーンと合わせる手間

#### 中間案
共有シーンは 1 つのまま、フィールドを Prefab にして Prefab モードで別々に編集する（Scene Fusion が Prefab の中の編集を同期するかは未確認、#43）。

#### シーンの重ね方（1 つのミニチュア = 複数のシーン）

加算ロードは、シーンを**切り替える**のではなく**重ねる**読み込み方。ミニチュアの村は 1 つで、その上の木・川・牧場などのフィールドを、それぞれ別のシーンファイルにしておき、全部を同時に読み込んで 1 つの村として見せる。

```
Bootstrap.unity    最初に読む。最後まで残る       XR リグ、AprilTag、VillageRoot（村の基準位置）
Village.unity      + 加算                         台・地面・道・家など、村全体で共有するもの
Field_Tree.unity   + 加算                         木のフィールド（木、リンゴの届け先、村人）
Field_River.unity  + 加算                         川のフィールド
Field_Ranch.unity  + 加算                         牧場のフィールド
                   ─────────────────────
                   = プレイヤーには、1 つの村に 4 つのフィールドがあるように見える
```

- 各フィールドのシーンは、**村の座標（`VillageRoot` を原点）で作る**。木のフィールドは村の左奥、川は右手前、のように、最終的な場所にそのまま置く。
- エディタでは、複数のシーンを同時に開ける（Hierarchy にシーンをドラッグする）。`Village` と `Field_Tree` を一緒に開けば、村全体を見ながら木のフィールドだけを編集・保存できる。
- 木の担当は `Field_Tree.unity` だけを、川の担当は `Field_River.unity` だけを保存するので、同時に作業してもファイルがぶつからない。
- チュートリアルで木と川しか使わないなら、その 2 つだけを読み込めばよい（読み込むフィールドはデータで決める）。

#### シーンを分けたときの位置合わせ

フィールドのシーンは、AprilTag で合わせた村の位置（`VillageRoot`）に付いて動く必要がある。ただし Unity では、**別のシーンにあるオブジェクトを、エディタ上で親にできない**（シーンをまたぐ参照は保存できない）。そこで、実行時につなぐ。

- Bootstrap のシーン（XR リグ、`VillageRoot`）は最初に読み込み、**最後まで捨てない**。フィールドのシーンは、その上に加算ロードする。
- フィールドのシーンは、ルートのオブジェクトを 1 つだけ持つ。読み込みが終わったら、Bootstrap がそのルートを `VillageRoot` の子にする（`Transform.SetParent`。子になったオブジェクトは、親のシーンへ移る。そのため、あとでフィールドのシーンを捨てても一緒には消えない。消したいときは、そのルートを自分で `Destroy` する）。
- `DontDestroyOnLoad` は要らない。`DontDestroyOnLoad` は、シーンを**切り替えて**前のシーンを捨てるときに、オブジェクトを残すための仕組み。ここでは加算ロードでシーンを捨てないので、Bootstrap のシーンがその役目を果たす。使うと、シーンを読み直したときに同じものが 2 つできる問題が起きやすい。
- **体験は途切れない。** 加算ロードは前のシーンを捨てないので、画面が暗転したり XR リグが作り直されたりしない。フィールドはプロローグの間など、見せる前に非同期で（`LoadSceneAsync`）読み込んでおく。読み込みの途中にフィールドが一瞬だけ原点に見えないよう、読み込むまでは非表示にしておく。
