# MTG の前提（Claude が議事録を作るときに読む）

MTG の録音から議事録や Issue を作る Claude は、この MTG の前提を知らない。**前提が足りないと、的外れな Issue や決定を作る。** この文書は、その前提を書いたもの。話し言葉の読み替えや、扱い方の決まりも書く。**間違いや古いところに気づいたら、PR で直す。**

仕組みの全体は [mtg-automation.md](mtg-automation.md)。

## 何を作っているか

- 触感デバイス（フォーク型）で、口の中の**食感**から食べ物・生物を見分け、それを**口から生み出して**、ミニチュアの村（山・海・草原・村）の必要な場所に**届ける**ゲーム。プレイヤーは**神様**
- IVRC に出した作品を GDC 向けに作り直している。**alt.ctrl.GDC 2027 に 10/29（日本時間）に応募**する（動画と英文が要る）。詳しくは [README](../README.md)、[応募のまとめ](alt-ctrl-gdc-application.md)
- 体験はすべて**英語**。1 人約 8 分。台本は [シナリオブック](scenario-book.md)
- 区切り（マイルストーン）: M1 見せるものが決まる（10/13）→ M2 デモが通しで動く（10/24）→ M3 応募（10/30）→ M4 入選後

## 話し言葉の読み替え

MTG では、画面を見ながら番号や略語で話す。次のように読む。

| 言い方 | 意味 |
|---|---|
| 「S3」「S4」など | [シナリオブック](scenario-book.md)の場面（S3 = チュートリアル 1: フォークの使い方） |
| 「39 番」「#54」「2 番」「3 番」 | 多くは Issue 番号。**その Issue のタイトルと話の中身が合うときだけ**そう読む。合わなければ、場面や資料の番号かもしれないので、決めつけない |
| 「デバイス」 | フォーク型の触感デバイス（フォーク + 口に含む部分のセット） |
| 「HMD」 | Meta Quest（頭に着ける画面） |
| 「雲」「霞」 | 体験者の周りに浮かぶ、恵みのもと。フォークで刺す（VR の中だけにある） |
| 「生み出す」「産む」「出す」 | 口から物を生み出す。「届ける」はそれをフィールドに届けること |
| 「食感」「触感」 | 同じものを指していることが多い |
| 「フィールド」「ゾーン」 | 山・海・草原・村の 4 つ（雪は山に含める） |
| 山・海・草原・村（ブランチ名・ファイル名で） | `mount`・`mountain` / `sea`・`ocean` / `grass` / `village`。人の名前が付くこともある（`tomita_grass`） |
| 「村人」「巫女」「神様」 | 村人はフィールドにいて欲しい物を見せる。巫女は語り手。神様はプレイヤー |
| 「Q1 は A」「Q2 はそれで」 | 議題 Issue の「Claude からの質問」への答え（Q の番号は、その回の議題の中だけで使う） |

## 決まっていること（蒸し返さない）

[decisions.md](decisions.md) と [README](../README.md) が正。とくに:

- 共有シーンは 1 つにして、Scene Fusion で一緒に編集する
- 神様コンセプトを前面に出す
- 出せるのは、見分けられる**数種類の食感**。食べ物そのものの食感（リンゴの食感など）は出さない
- 制限時間は 2 分（仮）。届け間違いは時間を失うだけ

未決のことは README「4. 未解決・要確認」と、`decision` ラベルの Issue。

## 議事録・Issue を作るときの決まり

- **雑談や脱線は、議事録に書かない。** 他のゲームの話、世間話、食事の話など。決定に関わるもの（例: 神設定が受け入れられるかの懸念）だけ、「参考」として 1 行
- **「〜かもしれない」「〜かな」「〜したらどう？」と一人が言っただけのものは案。** 決定にも方針にもしない。「そうしよう」「それで決定」「それでいこう」と合意が取れたものが、決まったこと。決定とまでは言えなくても、複数人が賛同している、または「〜の方向で」と進む流れがあるものは、**方針**として書く
- **新規 Issue は、具体的な作業が語られ、かつ既存の Issue にないものだけ。** 1 回の MTG で作るのは**最大 3 つ**。迷ったら作らず、議事録の「Issue にしたほうがよさそうなもの」に、題の案と根拠を書く（作るかどうかは人が決める）
- **既存の Issue と話が重なるなら、新規にせず、その Issue にコメントする。** MTG の議題になった Issue（議題 Issue からリンクされたもの）を、まず当てはめる
- **`decision` の Issue は、決まったか方針が出て、結果を文字で書けたら閉じる。** 図・表・docs の更新は任意で、完璧を求めない。残る作業は新しい Issue か、関連する Issue に分ける。方針はあるが閉じるほどでなければ、方針と残る問いをコメントして `mtg-decide` を外す。**作業の Issue（実装・ものづくりなど）は、自分の判断では閉じない**（ヒントや方針はコメントで残す。閉じるのは、`Closes` 付きの PR があるとき、または誰かが閉じるよう指示したとき）
- **担当者**: 「〇〇がやる」と言った人だけ書く。名前が聞き取れないときは空にする
- **英語や専門用語が崩れていたら、直さずに残す**（推測で別の語にしない）
- **「誰が・何で作ったか」（作成者、使った AI やツールの名前）は、はっきり聞き取れたときだけ書く。** 他の人の発言と重なった区間や、聞き取りが崩れた区間では、書かない（「Codex で作った」のような言い換えを、推測でしない）。シナリオブックなど、リポジトリの記録（Issue の冒頭の注記、コミット）で分かることは、記録を正とする

## プロジェクトの分野（議題で全体を見回すとき）

Issue は、作業を書いた人の目で切られている。**Issue だけを見ると、誰も Issue にしていない作業が見えない**（例: フォーク型デバイスを作ること、ハードとゲームをつなぐこと、展示の図面）。議題を作るときは、Issue ではなく分野ごとに、「次の区切りに要るもの」と「追えているもの」を比べる。

| 分野 | 要るものの出どころ | GitHub に残りにくいもの |
|---|---|---|
| ハードウェア（フォーク型デバイス、ファーム、通信、ゲームとの接続） | README のデバイス、`docs/architecture.md` 5 章 | 実物の製作、配線、試した結果 |
| ゲームのソフト（流れ、チュートリアル、届ける、本編） | README の体験フロー、シナリオブック | — |
| シーン（村、山・海・草原のフィールド） | #79 の決定、`docs/architecture.md` | 各自のサンドボックスでの作業 |
| 素材・音（モデル、見た目、英語の語り） | `docs/visual-direction.md`、シナリオブック | 作りかけの素材 |
| 応募（動画、英文、フォーム、展示の図面） | `docs/alt-ctrl-gdc-application.md` | — |
| ジオラマ・展示（台、予算、発注、衛生） | README、応募のまとめ | 発注、予算の申請、実物 |
| 進め方（担当、レビュー、Quest での確認） | CONTRIBUTING | 口頭・Slack での分担 |

右の列のものは、記録が無くても進んでいることがある。**Claude には「進んでいない」と「見えていない」の区別がつかない**ので、決めつけずに「どうなってる？」と聞く。

## Claude からの質問

Claude（議題・dev-loop・merge-check など）が、人に聞きたいことを書く形。**質問は、それが関わる Issue か PR にコメントで書く**（文脈がそこにあるので、人が答えやすい）。散らばっても拾えるように、最後の行に目印を入れる。水曜の議題（`mtg-agenda`）が、答えの無いものを集めて並べる。

**まず「どうなってる？」と開いて聞く。** Claude は GitHub の外（手で作っているハードウェア、手元の Unity、Slack、口頭）が見えない。見えないものに「〇〇でよいか？」と選択肢を出すと、Claude の思い込みの中から選ばせることになる。状況を知らないうちは、開いた質問にする。選択肢つきにするのは、状況は分かっていて、決めることだけが残っているときだけ。

| 種類 | 使うとき | 議題での置き場所 |
|---|---|---|
| **状況を聞く**（「〇〇って、どうなってる？」） | 記録が無い・止まって見える・Claude からは見えない作業 | 「共有すること」の「Claude から聞きたいこと」 |
| **決めてほしい** | 状況は分かっていて、選ぶことだけが残っている | 「決めること」の「Claude からの質問」 |

```
**Claude から聞きたいこと**: <開いた 1 文。「〇〇って、どうなってる？」の形>
- なぜ聞くか: <締切や、止まりそうな作業を 1 行>
- Claude に見えていること: <見た記録。無ければ「GitHub に記録なし」>

答えは、このコメントへの返信（コメント）か、MTG で。ひとことでよいです。
<!-- claude-question -->
```

```
**Claude からの質問**: <1 文>
- 選択肢: A. … / B. …
- 決めなければ: <Claude がそのまま進める案。進められないものは「止まったまま」>
- なぜ聞くか: <止まっている作業を 1 行>

答えは、このコメントへの返信（コメント）か、MTG で。
<!-- claude-question -->
```

- **人の答え方は自由**（返信のコメント、MTG で話す、Issue の本文を直す、のどれでもよい。ひとことでよい）。形をそろえるのは Claude の側
- 1 つのコメントに質問は 1 つ。同じ Issue に、答えの無い同じ質問をもう一度書かない
- 答えが済んだ印: 質問より後の人のコメント、または `<!-- claude-answer -->` を含むコメント（MTG の答えを mtg-sync が書いたもの）
- Claude のコメントは、代表者のアカウントから投稿されるので、**投稿者では人と区別できない**。`<!-- claude` で始まる目印、`Generated by [Claude Code]`・`Generated with [Claude Code]`、または「AI 生成のため」の一文を含むものを Claude のコメントとみなす。**これから Claude が書くコメントには、必ず最後の行に `<!-- claude -->` を入れる**（`<!-- claude-question -->` などの目印があるものは、それでよい）。古いコメントには目印が無いので、上の 3 つで見分ける
- 人が書くこと（形式は自由）と、Claude が書くこと（目印つきの決まった形）を分けるのは、**人は書きやすさ、Claude は拾いやすさ**を優先するため
