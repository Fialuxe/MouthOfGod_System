# mtg-sync

MTG の文字起こしから、議事録・Issue・docs を更新する。**無人で最後まで実行する**。確認のために止まらない。迷う項目は、実行せずに議事録の末尾へ書く。

## 入力
- 文字起こし: `<name>.clean.txt`（`tools/mtg/clean.py` で幻覚と繰り返しを除いた、`[MM:SS] 発言` 形式）
- MTG の日付（プロンプトで渡される。無ければファイルの更新日）

## 前提
- 文字起こしは Whisper の出力で、固有名詞や数字の誤認識がある。話者は区別されない。
- このリポジトリは**公開**。文字起こしの全文は Issue・PR・コミットに載せない。書くのは決定事項と要点だけ。雑談や個人的な発言は書かない。
- 文字数は少なく。議事録は 40 行を目安に、短く。

## 試運転モード
プロンプトに「試運転」とあるときは、**GitHub にも、リポジトリのファイルにも、何も書き込まない**。手順 1〜3（校正、読む、判断する）だけを行い、手順 4〜6 でやるはずだった内容を、文字起こしと同じフォルダの `<名前>.proposal.md` に書く。`gh` は読み取り（`issue list`・`issue view`・`pr list`）だけを使う。proposal.md には、実行したはずの操作を 1 件ずつ（対象の Issue 番号、コメント全文、新規 Issue の題と本文、クローズの理由と発言の MM:SS）書く。`corrections.tsv` への追記案も、書き込まずに proposal.md に書く。

## 手順

### 1. 校正する
`clean.txt` を、次を手がかりに読み直し、`<name>.corrected.txt` に書く（ローカルのみ。コミットしない）。
行頭の `?` は、Whisper 自身が自信を持てなかった行（聞き取りが崩れている可能性が高い）。まずそこを重点的に直す。
ただし `?` が付かない行にも、自信を持った誤認識が残る（例: 「時給」が「地球」）。**全体を通読して、文脈に合わない語も直す。**
- `tools/mtg/glossary.txt` と `tools/mtg/corrections.tsv`
- open の Issue のタイトル、`docs/` の用語、README の用語

直す対象は、**発音が近く、文脈から言い換え先が一つに決まる誤認識**（例: 「見せる版」→「Scene Fusion」）に限る。聞き取れない箇所は推測で埋めない。人名は、同じ MTG の中の別の聞き取りと突き合わせて確信が持てるものだけ直す。
同じ誤認識が繰り返し出ていて、直し方に確信があるものは `tools/mtg/corrections.tsv` に `誤<TAB>正` で追記する（最大 10 件。PR に含まれる）。

### 2. 読む
**前提を先に読む。前提が足りないと、的外れな Issue や決定を作る。**
- **[docs/mtg-context.md](../../../docs/mtg-context.md)**（話し言葉の読み替え、決まっていること、議事録・Issue を作る決まり）。**この決まりを守る**
- README の「1. コンセプト」「2. ゲームの骨子」「4. 未解決・要確認」と、`docs/scenario-book.md` の場面一覧、`docs/decisions.md`
- **議題 Issue の本文と、そこからリンクされた Issue（本文と、直近のコメント 10 件）。** その MTG で何を話すはずだったかが、一番の手がかり
- 校正した文字起こし
- [CONTRIBUTING.md「作業の進め方」](../../../CONTRIBUTING.md)（MTG の運用とラベルの意味）
- 議題 Issue: 題が「M/D MTG の議題と議事録」の open な Issue のうち、MTG の日付に合うもの（`gh issue list --label "MTGで共有" --state open`）。無ければ、手順 5 の議題 Issue を新規に作る
- `MTGで共有`・`MTGで決める` が付いた open の Issue（本文も）
- open の Issue 全体（`gh issue list --limit 200 --json number,title,labels,milestone,assignees`）

### 3. 判断する
先に、文字起こしを**話題ごとに区切り**、それぞれを議題 Issue・既存の Issue・シナリオの場面に**対応づける**（話に出た「39 番」「S3」などは、`mtg-context.md` の読み替えに従う）。対応づけられない話題は、雑談か、前提が足りないもの。**雑談は無視し、前提が足りないものは Issue にせず、議事録の「確認してほしいこと」に書く。**

- **決まったこと**: 明確な合意がある（「これでいこう」「〇〇で決定」など）ものだけ。議論が続いたものは「決まらなかった」にする。
- **次にやる人**: 発言で担当が明らかなときだけ書く。曖昧なら担当を空にして、議事録の末尾に書く。
- **クローズ**: その Issue の完了条件を満たしたと、発言で明確に言えるときだけ。理由と発言の MM:SS をコメントに残す。確信が持てないものは閉じず、議事録に「クローズ候補」と書く。
- 既存の Issue と重なる話題は、新規にせず既存にコメントする。

### 4. 実行する
`gh` で次を行い、実行した番号と URL を覚えておく。
1. **決めた Issue**: 決定内容を短くコメントし、`MTGで決める` を外す。決まらなかったものは付けたままにする。
2. **共有した Issue**: `MTGで共有` を外す。
3. **クローズ**: 手順 3 の条件を満たすものだけ。コメントに「MTG (M/D) で完了と確認」と理由を書く。
4. **新規 Issue**: 出てきた作業・決めごとのうち、既存にないもの。**最大 3 つ**（`mtg-context.md`）。作業の種類ラベルと **`Claude提案`** を付け、マイルストーンを設定する（README「プロジェクト管理」）。Blocked by が明らかなら設定する。
5. **docs**: 決めたことは `docs/decisions.md` の先頭に、既存の書式で追記する。

### 5. 議事録を書く
- 議題 Issue に議事録をコメントする（無ければ、題「M/D MTG の議事録」の Issue を作ってそこに書く）。構成: **共有したこと / 決めたこと / 次にやる人 / 片づけた Issue（番号つき） / 確認してほしいこと**（迷って実行しなかったもの。無ければ省略）。
- 同じ内容を `docs/minutes/YYYY-MM-DD.md` に書く。
- 議題 Issue を閉じる。次回の議題 Issue は作らない（水曜に別のルーティンが作る）。

### 6. PR にする
ブランチ `docs/mtg-YYYYMMDD` を `origin/main` から切り、`docs/minutes/YYYY-MM-DD.md`・`docs/decisions.md`・`tools/mtg/corrections.tsv` の変更だけをコミットして push し、PR を作る。本文は `.github/pull_request_template.md` の形で、`Closes #` は議題 Issue 以外で終わるものが無ければ消す。**マージはしない。**

### 7. 報告する
実行したこと、見送ったことを 5 行以内で出力する。失敗した手順があれば、止まらずに続け、報告に書く。
