# mtg-sync

MTG の文字起こしから、議事録・Issue・docs を更新する。**無人で最後まで実行する**。確認のために止まらない。迷う項目は、実行せずに議事録の末尾へ書く。

## 入力
- 文字起こし: `<name>.clean.txt`（`tools/mtg/clean.py` で幻覚と繰り返しを除いた、`[MM:SS] 発言` 形式）
- MTG の日付（プロンプトで渡される。無ければファイルの更新日）

## 前提
- 文字起こしは Whisper の出力で、固有名詞や数字の誤認識がある。話者は区別されない。
- このリポジトリは**公開**。文字起こしの全文は Issue・PR・コミットに載せない。書くのは決定事項と要点だけ。雑談や個人的な発言は書かない。
- 文字数は少なく。議事録は 40 行を目安に、短く。

## クラウドで動かすとき（ルーティンから呼ばれる）
文字起こしのクラウドジョブが、ルーティンの API を呼ぶ。プロンプトは `date=YYYY-MM-DD name=<名前>`。PC は無い。次の点だけ、上の手順と違う。
- リポジトリは 2 つ（公開の `MouthOfGod_System`、非公開の `MouthOfGod_transcripts`）。非公開のほうを、作業ディレクトリの隣へ `git clone` する（clone できなければ、何もせず、その旨を報告して終わる）。文字起こしは `<非公開>/<date>/<name>.clean.txt`。
- **最初に確認する**: `<非公開>/<date>/<name>.minutes.done` があれば、何もせず終わる。`docs/minutes/<date>.md` が `origin/main` に、または `claude/mtg-<日付8桁>` ブランチが origin にあれば、議事録は済んでいる。`.minutes.done` だけ書いて終わる。
- `activity.md`: MTG の前日 0 時（UTC）を開始として `python tools/mtg/activity.py <開始時刻(UTC)> <出力先>` で作る。
- 校正した `corrected.txt` と `activity.md` は、コミットしない。
- 手順 6 のブランチは **`claude/mtg-YYYYMMDD`**（クラウドでは `claude/` 以外のブランチへ push できない）。
- 手順 6 のあと、非公開リポジトリの `<date>/<name>.minutes.pending` を `.minutes.done`（中身は `{"done": <ISO 時刻>, "host": "cloud-routine"}`）に置き換えてコミットし、push する。失敗時は `.pending` を残す（PC の見張りが、6 時間後に引き継ぐ）。
- 公開リポジトリに文字起こしの全文・ファイル名を書かない決まりは、そのまま。

## 試運転モード
プロンプトに「試運転」とあるときは、**GitHub にも、リポジトリのファイルにも、何も書き込まない**。手順 1〜3（校正、読む、判断する）だけを行い、手順 4〜6 でやるはずだった内容を、文字起こしと同じフォルダの `<名前>.proposal.md` に書く。`gh` は読み取り（`issue list`・`issue view`・`pr list`）だけを使う。proposal.md には、実行したはずの操作を 1 件ずつ（対象の Issue 番号、コメント全文、新規 Issue の題と本文、クローズの理由と発言の MM:SS）書く。`corrections.tsv` への追記案も、書き込まずに proposal.md に書く。

## 手順

### 1. 校正する
`clean.txt` を、次を手がかりに読み直し、`<name>.corrected.txt` に書く（ローカルのみ。コミットしない）。
行頭の `?` は、Whisper 自身が自信を持てなかった行（聞き取りが崩れている可能性が高い）。まずそこを重点的に直す。
ただし `?` が付かない行にも、自信を持った誤認識が残る（例: 「時給」が「地球」）。**全体を通読して、文脈に合わない語も直す。**
- `tools/mtg/glossary.txt` と `tools/mtg/corrections.tsv`
- open の Issue のタイトル、`docs/` の用語、README の用語

直す対象は、**発音が近く、文脈から言い換え先が一つに決まる誤認識**（例: 「見せる版」→「Scene Fusion」）に限る。聞き取れない箇所は推測で埋めない。人名は、同じ MTG の中の別の聞き取りと突き合わせて確信が持てるものだけ直す。
同じ誤認識が繰り返し出ていて、直し方に確信があるものは `tools/mtg/corrections.tsv` に `誤<TAB>正` で追記する（最大 10 件。PR に含まれる）。

### 2. 読む
**前提を先に読む。前提が足りないと、的外れな Issue や決定を作る。**
- **[docs/mtg-context.md](../../../docs/mtg-context.md)**（話し言葉の読み替え、決まっていること、議事録・Issue を作る決まり）。**この決まりを守る**
- README の「1. コンセプト」「2. ゲームの骨子」「4. 未解決・要確認」と、`docs/scenario-book.md` の場面一覧、`docs/decisions.md`
- **議題 Issue の本文と、そこからリンクされた Issue（本文と、直近のコメント 10 件）。** その MTG で何を話すはずだったかが、一番の手がかり
- **議題 Issue の、人のコメント**（`docs/mtg-context.md`「Claude からの質問」の見分け方で、Claude のものを除く）。**人が自分で足した話題で、本文（Claude の下書き）より優先する。** 話題の区切りと対応づけは、まずこれに当てはめる。形式は人によって違う（見出しだけ、箇条書き、文章）。形をそろえずに、中身で読む
- **`<名前>.activity.md`**（MTG の前日から今までの Issue・PR・コメント・ラベル変更・main のコミット。`run.ps1` が作る。無ければ `python tools/mtg/activity.py <開始時刻(UTC)> <出力先>` で作る）。**全部読む。** さらに、その中の次のものは `gh issue view N --comments` で全文を読む: 議題 Issue、`mtg-decide`・`mtg-share` の Issue、MTG の最中・後にコメントされた Issue
- 校正した文字起こし
- [CONTRIBUTING.md「作業の進め方」](../../../CONTRIBUTING.md)（MTG の運用とラベルの意味）
- 議題 Issue: `gh issue list --label "mtg-share" --state open` から、題に「議題と議事録」を含み、**MTG の日付以前に作られた**もののうち、題の日付（M/D）が MTG の日付に合うもの、題に日付が無ければ作成日が MTG の日付に最も近いもの。MTG の日付より**後の日付**の議題 Issue（次回分）は選ばない。どれも無ければ、手順 5 で新規に作る
- `mtg-share`・`mtg-decide` が付いた open の Issue（本文も）
- open の Issue 全体（`gh issue list --limit 200 --json number,title,labels,milestone,assignees`）

### 3. 判断する
先に、文字起こしを**話題ごとに区切り**、それぞれを議題 Issue・既存の Issue・シナリオの場面に**対応づける**（話に出た「39 番」「S3」などは、`mtg-context.md` の読み替えに従う）。対応づけられない話題は、雑談か、前提が足りないもの。**雑談は無視し、前提が足りないものは Issue にせず、議事録の「未解決・次回」に書く。**

- **決まったこと**: 明確な合意がある（「これでいこう」「〇〇で決定」「とりあえずそれで」など）もの。
- **方針**: 決定とまでは言えないが、複数人が賛同している、または「〜の方向で」と進める流れが読み取れるもの。「方針」と分けて書く。一人が「〜かな」と言っただけのものは案であって、方針にもしない。議論が続いて流れも出なかったものは「決まらなかった」にする。
- **次にやる人（担当の役割は 3 つ）**: **Leading**（進める・決める人。1 人）、**Support**（Leading を助ける人。1 人）、**Follower**（それ以外の全員。進み具合を見て、必要なら意見を言う）。`decision` の Issue も同じ。発言で明らかなときだけ書く。Leading が曖昧なら、議事録の「アクション」に Leading「未定」と書き、「未解決・次回」に「Leading を決める（#N）」と 1 行足す（水曜の議題が、これを拾って次の MTG で決めてもらう）。Support は、発言にあるときだけ書き、無ければ空でよい。Follower は書かない（全員が Follower）。
- **クローズ（`decision` ラベルの Issue）**: その Issue で決めたかったことが、決まったか、方針が出ていて、**結果を文字で伝わる形で書ける**なら閉じる。**図・表・docs の更新などの成果物は任意**（無くても閉じてよい）。残る作業があれば、新規 Issue（最大 3 つの枠内）か、既存の関連 Issue に分ける。
- **作業の Issue（`enhancement`・`making/hardware` など）は、作業や対応の状況が変わって、終わったことが確かめられたら閉じる。** ヒントや気づき、方針はコメントとして残す。閉じるのは次のときだ: (a) その Issue を `Closes` する PR がある（マージで自動的に閉じる。自分ではクローズしない。PR 番号をコメントする）、(b) MTG の発言や Issue のコメントで、作業が終わった・対応が済んだ・不要になったと分かる（例: ハードウェアができた、部品が届いた、別の方法に変わった）。その発言や記録をコメントに引いて閉じる。**閉じられるものは、その場で閉じる。「閉じられそう」と書くだけで終わらせない。** 発言や Issue のコメントで終わったことが読み取れ、手順 4 のコメントに根拠（録音の時刻、コメントの引用）を書けるなら、閉じる。閉じるのをためらうのは、根拠が発言にない（推測が要る）ときだけ。そのときは閉じずに、議事録の「未解決」に、番号と、何が分かれば閉じられるかを 1 行で書く。
- **方針が出ていて、残りが作業のもの（`decision` の Issue）は、閉じる。** 残る作業（図を作る、試す、書く、案から選ぶ など）は、**それを直接止めている実装の Issue**（`gh api repos/{owner}/{repo}/issues/N/dependencies/blocking` で調べる。無ければ関連する Issue）の「やること」に、「（#N から移した）」と付けて移し、閉じるときのコメントに、決まったことと移した先を書く。担当が一人で決められる残りの問いは、移した先の Leading が決める。
- **方針はあるが、残りの問いが、グループで決めるものである Issue**: 閉じずに、方針と残る問いを短くコメントし、`mtg-decide` を外す（次の状態へ進める）。
- **Claude から聞きたいことへの答え**（議題の「共有すること」）: 話に出た状況を、議事録の「議題ごとの要点」に書く。答えで、**Issue になっていない作業**（例: デバイスの製作を誰かが進めている）が分かったら、「Issue にしたほうがよさそうなもの」に回す。関わる Issue があれば、そこにも 1 行コメントする（最後の行に `<!-- claude-answer -->`）
- **Claude からの質問への答え**: 議題 Issue の「Claude からの質問」の Q 番号ごとに、答えが出たか（「Q1 は A」、選択肢の中身を言った、など）を判断する。答えが出たものは、手順 4 で元のコメントの Issue・PR に返す。決まらなかったものは何もしない（次の議題に持ち越される）
- 既存の Issue と重なる話題は、新規にせず既存にコメントする。
- **MTG の最中・後に、すでに誰かが書いたことは、重複して書かない。** Issue のコメント・本文・ラベル・担当・クローズ、できた PR で、すでに反映されているものが対象。議事録には「#N に〇〇が書いた」とリンクだけ置く。bot（`github-actions`）の自動更新は無視する。
- **文字起こしの解釈と、人が書いた記録が食い違うときは、人が書いた記録を正とする**（文字起こしは聞き間違いがありうる）。食い違いは、議事録の「未解決・次回」に書く。
- **関連する PR（open・merged）がある話題は、Issue のコメントに PR 番号を入れる。** PR が `Closes` する Issue は、自分でクローズしない。マージ済みの PR で解決した話題は「済み」として扱う。
- 新規 Issue は、`activity.md` にある、MTG の後にできた Issue（子 Issue など）と重ならないようにする。
- **理由・経緯は、発言にあるものだけを書く。言っていない理由を補わない**（`decisions.md` の「理由」も同じ）。理由が語られていなければ「理由は MTG では語られなかった」と書く。
- **聞き取りが崩れた区間（`?` が続く箇所など）の中身を、推測で説明しない。** 「聞き取れず内容不明」と書く。
- 「作った」「作り直した」「直した」など、動作の言い方は発言のとおりにする。
- **作成者や、使った AI・ツールの名前は、はっきり聞き取れたときだけ書く。** 発言が重なった区間や、聞き取りが崩れた区間では書かない。校正で、固有名詞を別の語（ツール名など）に言い換えるのは、`glossary` や Issue・docs にその語がある場合だけ。

### 3.5 不要になった（deprecated）可能性のある Issue を確認する
**議事録を書く前に**、open の Issue（`gh issue list --limit 300`）のうち、**この MTG の決定・方針、または `docs/decisions.md` の記録と、前提が食い違うもの**を探す。例: 決定でやらないことになった作業、題や本文が古い前提（旧案のフィールド構成、やめた方式）のままのもの、別の Issue に統合されたもの。すでに `deprecated` ラベルが付いた Issue は対象外。
- 見つけたら、その Issue に「MTG (M/D) の〇〇により、この Issue は不要、または書き換えが必要かもしれません（根拠: #N、録音 MM:SS 付近）。」とコメントし、議事録の「見直し候補」に、番号と 1 行の理由を書く（**最大 5 件**）。
- **`deprecated` ラベルを付ける・閉じるのは、自分では行わない**（作業の Issue と同じ。人が決める）。誰かが「これはもういらない」「deprecated にして」と指示したときだけ、`deprecated` ラベルを付けて閉じる（旧計画の Issue の扱いに倣う）。
- 根拠が弱いものは、コメントも議事録への記載もせず、見送る。題だけが古い（本文は直っている）ものは、「題の見直し候補」とだけ書く。

### 3.6 Blocked by（先に終わっている必要があるもの）を確認する
議事録を書く前に、**MTG で触れた Issue と、決定・方針で前提が変わった Issue**について、GitHub の Blocked by（Relationships）を読む（`gh api repos/{owner}/{repo}/issues/N/dependencies/blocked_by`。本文の「つながり」の文字ではなく、こちらが正）。次を探す:
- 決定や方針で、**先に終わっている必要がなくなった**もの（やめた作業、置き換わった作業を指している）
- 決定や方針で、**新しく先に必要になった**もの（MTG で新しくできた Issue、順番が逆になったもの）
- **閉じた Issue や `deprecated` の Issue を、まだ指している**もの
- 本文の「つながり」と、Blocked by の設定が食い違っているもの
見つけたら、その Issue にコメントし、議事録の「見直し候補」に書く（手順 3.5 と合わせて最大 5 件）。**Blocked by の付け外しは、自分では行わない**（ロードマップと、小ゴール Issue の自動クローズが変わるため。人が決める）。例外は、手順 4 で作る新規 Issue に、先に必要なことが明らかな Blocked by を付けるときだけ。

### 4. 実行する
**この手順と手順 5 で書くコメントには、すべて最後の行に `<!-- claude -->` を入れる**（人のコメントと見分けるため。`docs/mtg-context.md`「Claude からの質問」）。
`gh` で次を行い、実行した番号と URL を覚えておく。
1. **決めた Issue・方針が出た Issue**: 決定内容（方針なら「方針」と明記）と、残る問いを短くコメントし、`mtg-decide` を外す。決まらず、方針も出なかったものは付けたままにする。
2. **共有した Issue**: `mtg-share` を外す。
3. **クローズ**: 手順 3 の条件を満たすものだけ。コメントは次の定型で、簡潔に書く: 「M/D ミーティング、録音 MM:SS 付近を参照。〇〇だと決まった（方針が出た）。ただし AI 生成のため、誤っている場合は reopen してください。」「やること」「できたと言える状態」のチェックボックスは、満たしたものだけ `gh issue edit` で `[x]` にする（成果物が任意のものは、コメントに「任意のため省略」と書く）。
4. **新規 Issue**: 出てきた作業・決めごとのうち、既存にないもの。**最大 3 つ**（`mtg-context.md`）。作業の種類ラベルと **`claude-proposal`** を付け、マイルストーンを設定する（README「プロジェクト管理」）。Blocked by が明らかなら設定する。 **`decision` の Issue を作るときは、`.github/ISSUE_TEMPLATE/decision.md` の形で書き、「決めたあとの行き先」（残る作業を移す、実装の Issue）を必ず書く。行き先が書けないものは、`decision` にせず、「Issue にしたほうがよさそうなもの」に回す。**
   - **作った後に、マイルストーンが適切か考え直す。** README「区切りの流れ」、各マイルストーンの期限（`gh api repos/{owner}/{repo}/milestones`）、Blocked by の先の Issue の区切りと照らし、期限に間に合うか・依存の順序が合うかを確認する。合わなければ設定し直し、コメントに理由を 1 行書く。
   - **担当者（Assignee）**: 発言で「〇〇がやる」と言った人を付ける。名前から GitHub ID への変換は、プロンプトで渡される `members.local.tsv`（`名前<タブ>GitHub ID`）で行う。ファイルが無い・名前が見つからない・聞き取りが怪しいときは、付けない。
   - **GitHub の Assignee には、Leading と Support の最大 2 人を付ける。Follower は付けない**（付けなくても全員が Follower）。どちらが Leading かは、Issue のコメント（手順 5 のコメントの先頭）と、議事録の「アクション」の表に書く。
   - **担当をそろえる**: 発言で Leading（と Support）が決まった Issue に、すでに多くの人（例: 全員）の担当が付いているときは、**発言で名前が出た人だけを残し、ほかの人を外す**。名前が出ていないときは、外さない（増やすのは構わないが、減らすのは発言があるときだけ）。外したときは、コメントに「M/D ミーティングで Leading が〇〇、Support が△△に決まったため、ほかの担当を外しました。ほかの人は Follower です」と書く。
5. **「次にやる人」に挙がった Issue（担当者が付いているもの、または発言で担当が決まったもの）には、必ず、期限と進め方を書いたコメントを付ける。** 実行ごとにコメントする Issue が揺れても、漏れないようにするため。期限が語られていなければ「期限は MTG では決まらなかった」と書く。すでに同じ内容が書かれている Issue には付けない（重複しない）。コメントは「Leading: @〇〇、Support: @△△（無ければ省略）。M/D ミーティング（録音 H:MM:SS〜H:MM:SS）: 〇〇まで、…。（AI 生成のため、誤っている場合は訂正してください）」の形で、簡潔に。
6. **マイルストーンの見直し候補**: MTG で触れた既存の Issue のうち、期限が過ぎた区切りのまま、決定で優先度が変わった、などで区切りが合わなくなったものは、Issue に「マイルストーンの見直し候補: M1 → M2。理由: …」とコメントする（**変更は人が行う**）。
7. **docs**: 決めたことは `docs/decisions.md` の先頭に、既存の書式で追記する。
8. **Claude からの質問の答え**: 答えが出た質問ごとに、元のコメントがある Issue・PR に、「M/D ミーティング（録音 MM:SS 付近）での答え（Q1）: 〇〇。（AI 生成のため、誤っている場合は訂正してください）」とコメントし、最後の行に `<!-- claude-answer -->` を入れる（これで、次の議題に持ち越されない）。答えで Issue の仕様が決まったなら、その Issue の本文は変えず、コメントだけにする（dev-loop の PM は、コメントも仕様として読む）

### 5. 議事録を書く
- 議題 Issue に議事録をコメントする（無ければ、題「M/D MTG の議事録」の Issue を作ってそこに書く）。構成（この順で書く。一般的な議事録の形。結論を先に置く。ひな形は `docs/templates/minutes-template.md`、例は `docs/templates/minutes-example.md`）: **日時・参加者（欠席者）/ 決定事項（決定と方針を 1 つにまとめ、方針には「（方針）」と付ける。各項目に Issue 番号）/ アクション（表。Leading・Support・何を・いつまで・Issue。決まっていない役割は「未定」、期限が決まらなければ「未定」）/ 閉じた Issue（番号と 1 行の根拠）/ Issue にしたほうがよさそうなもの（話に出たが、まだ Issue にしていない作業・決めごと。上限 3 つの枠を超えたもの、確信が持てないものを含む。題の案（「〜する」の形で、何をするか分かるもの）・種類ラベルの案・根拠（録音の時刻）を 1 件 2 行以内で。最大 5 件。無ければ省略。自分では作らない）/ 議題ごとの要点（1 議題 1〜2 文。決定事項に書いたことは繰り返さない。雑談は書かない）/ 未解決・次回（決まらなかったこと、閉じる判断がつかなかった Issue、聞き取れなかった箇所、次回の議題の元になること。無ければ省略。聞き取りに自信のない箇所は、本文に「（聞き取り不明）」と書く）/ Claude の質問への答え（Q 番号・答え・返したコメントの Issue 番号。答えが無かった Q は「持ち越し」。質問が無ければ省略）/ MTG の後の動き（関連する新しい PR・Issue を 3 行以内。すでに書かれたことへのリンク） / 見直し候補（手順 3.5・3.6。不要・書き換えが必要かもしれない Issue。最大 5 件。無ければ省略）**。「確認してほしいこと」という見出しは作らない（一般的な議事録にない）。迷って実行しなかったものや、人が判断・修正しないと先に進めないことは、「未解決・次回」に最大 3 件まで書く。「触らなかった Issue」「人名を使わなかった」などの報告は書かない。
- 同じ内容を `docs/minutes/YYYY-MM-DD.md` に書く。
- 議題 Issue を閉じる。次回の議題 Issue は作らない（水曜に別のルーティンが作る）。

### 6. PR にする
ブランチ `docs/mtg-YYYYMMDD` を `origin/main` から切り、`docs/minutes/YYYY-MM-DD.md`・`docs/decisions.md`・`tools/mtg/corrections.tsv` の変更だけをコミットして push し、PR を作る。本文は `.github/pull_request_template.md` の形で、`Closes #` は議題 Issue 以外で終わるものが無ければ消す。**マージはしない。**

### 7. 報告する
実行したこと、見送ったことを 5 行以内で出力する。失敗した手順があれば、止まらずに続け、報告に書く。
