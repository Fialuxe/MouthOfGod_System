# dev-loop

> この仕組みを直す前に、[仕組みの前提](../../../docs/automation-premise.md) を読む（補助線であって決まりではない。人の負荷を増やさない）。

人に聞かず、最後まで進める。**1 回の実行で PR は 1 件まで。マージ・Issue のクローズ・ラベル/担当の変更はしない。**

## 手順
0. **決まりを読む**: 何をする前にも、**[CONTRIBUTING.md](../../../CONTRIBUTING.md) の 2 章（ブランチ運用）・5 章（レビュー）・6 章（スクリプト方針）**を読む。ブランチ名、コミットメッセージ、PR の作り方は、そこに従う。`claude/` で始まる名前は、決まりにない（下の例外を除く）。
1. **選ぶ**: `pm` サブエージェントを呼び、Issue を 1 件選んで実装の指示を出させる（あわせて、決定・議事録と食い違う「不要かもしれない Issue」にコメントさせる。ラベル付け・クローズはしない）。「該当なし」なら、そう報告して終わる（PR も Issue も作らない）。
2. **ブランチ**: PM が示した**ベース**から、**CONTRIBUTING 2 章の接頭辞**で切る。主に何を変えるかで選ぶ: スクリプト・Prefab・設定の追加は `feature/<内容>`、バグ修正は `fix/<内容>`、ドキュメントのみは `docs/<内容>`（`scene/` は使わない。シーンは触らない）。`<内容>` は英語の短い名前（例: `feature/mock-device`）。**`claude/` を接頭辞に使わない。** 例外: push が拒否されたとき（ルーティンの設定で、`claude/` 以外へ push できない場合）だけ、同じ名前に `claude/` を付けて（`claude/feature/mock-device`）push し、PR の本文にその旨を 1 行書く。ベースが `main` なら `origin/main`、積み PR なら前提の PR のブランチ（`origin/<そのブランチ>`）。積み PR のときは、`git log` で前提の変更が入っていることを確かめてから実装する。
3. **実装**: `engineer` を呼ぶ（PM の指示を丸ごと渡す）。
4. **レビュー**: `reviewer` を呼ぶ（Issue 番号とベースだけを渡す。engineer の説明は渡さない）。**差分に `Assets/` 以下のファイルが含まれるときは、`unity-reviewer` も呼ぶ**（同じ渡し方）。どちらかが「要修正」なら、両方の指摘をまとめて engineer に渡して直させ、直したあと、指摘したほうをもう一度呼ぶ。**2 往復して「承認」にならなければ、直らない指摘を PR の本文に書き、`needs-human` の扱いで PR を作る**（ドラフトにする）。`unity-reviewer` の「要確認（Unity で）」は直さずに、PR の本文の「Unity で確かめること」に書く。
5. **PR**: `.github/pull_request_template.md` の形で作る。**積み PR のときは、PR のベースを前提の PR のブランチにし**（`main` にしない）、本文の先頭に「#M（前提の PR）の上に積んでいます。#M がマージされたら、ベースを `main` に変更してください」と書く。`Closes #N` は、そのままでよい。`Closes #N`（その Issue を終わらせる PR のとき）、変更内容、動作確認（走らせたテストの結果、未確認のこと）。本文には「Unity で確かめること」（`unity-reviewer` を呼んだとき）、「判断した点」（engineer が推測で決めたこと）と「人が決める点」（reviewer が挙げたもの）の節も入れる。「人が決める点」があるときは、その節を `docs/mtg-context.md`「Claude からの質問」の形（1 点ずつ、選択肢と「決めなければ」つき）で書き、節の最後に `<!-- claude-question -->` を入れる（水曜の議題が拾い、MTG で答えてもらう）。無ければ「なし」とだけ書き、目印は入れない。最後に、reviewer の最終判断を 1 行。Issue に 1 行コメントで PR へのリンクを書く（最後の行に `<!-- claude -->`）。
6. **報告**: 選んだ Issue、PR の番号、レビューの往復数、未確認のこと、PM が見つけた「不要かもしれない Issue」（番号と 1 行の理由）を 8 行以内で出力する。Issue が選べず「該当なし」のときも、不要かもしれない Issue は報告する。

## 積み PR をまたいだあと
前提の PR が更新された（push された）ことに気づいたら、このルーティンでは直さない。人がマージするときに、ベースの変更とコンフリクトの解消を行う。報告には、積んだことと前提の PR 番号を書く。

## 止まる条件（PR を作らずに報告して終わる）
- テストが直せず、赤いまま
- 選んだ Issue（または関連する Issue）のコメントが全部読めなかった
- 変更が 5 ファイルを超えそうになった（Issue が大きすぎる。報告に「分割が要る」と書く）
- Issue の内容が読んで分からない
