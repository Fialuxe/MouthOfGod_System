# suggest-leading

> この仕組みを直す前に、[仕組みの前提](../../../docs/automation-premise.md) を読む（補助線であって決まりではない。人の負荷を増やさない。責めない・順位をつけない）。

担当（Leading）がいない Issue に、**候補の一覧**を作る。決めるのは人で、ここで挙げるのは材料だけ。狙いは、**効率を落とさず、かつ誰の可能性も狭めない**こと。

## 守ること（先に読む）
- **1 人を推さない。** 候補は 2〜4 人。順位をつけない。「この人が最適」と書かない。
- **評価の言葉を書かない。** 「コメントが少ない」「やる気がない」のような、人の評価に読める言葉は使わない。書くのは、事実と、そこから言える「この作業との相性」だけ。
- **候補に必ず入れるもの**: (1) これまでの関わりが深い人 (2) 引き継ぎのしやすさから見て、別の人が担当する場合の人 (3) **まだこの領域に関わっていない人**（新しく関わる機会。意向が見えるときだけ。見えなければ「立候補を歓迎します」と書く）。
- **本人の意向を最優先する。** 議事録・コメントに「やりたい」「興味がある」「触ってみたい」と書いた人は、候補に入れて、その発言を引く。逆に「手が埋まっている」「不在」と書いた人は、理由を添えて候補から外す、または負荷を明記する。
- **記録が見えない領域は、見えないと書く。** Claude は GitHub の外（手元の Unity、サンドボックスのシーン、ハードウェア、Slack、口頭）が見えない。記録が少ない人を「関わっていない」と決めつけない。`docs/mtg-context.md`「プロジェクトの分野」の注意と同じ。
- **非公開の情報を、公開の場に書かない。** 議事録は `docs/minutes/`（公開）を使う。文字起こしの全文と、カレンダーの個人の予定（非公開）は、判断の材料にしてよいが、中身を公開の Issue・コメントに書き写さない。
- 公開リポジトリに書く。人を傷つけうる言い方（比較して下げる、能力を推し量る）をしない。

## 材料（Issue ごとに集める）
1. **関わりの深さ**（事実だけ）: **その Issue と、つながる Issue（親・Blocked by・Blocking）にコメントした人**、その Issue が触る場所（`Assets/Scripts/<機能>`、`docs/`）の `git log` の作者・PR の作者、過去の担当。
   - **注意**: Claude の作業は、代表者（`Fialuxe`）のアカウントで投稿・コミットされる。そのため、コミットの作者だけを数えると、代表者に偏って見える。コミットの作者名が `Claude` のもの、`Co-Authored-By: Claude` のもの、dev-loop の PR は、代表者の実績に数えない。
2. **引き継ぎのしやすさ**: その領域の README・設計書（`docs/architecture.md` など）・コメント・PR の本文の量と、Issue の経緯の残り方。**Issue の「やること」と「できたと言える状態」が具体的か**（手順が書かれているか、テストの条件があるか）も見る。
   - 残っている → 別の人が引き継ぎやすい。担当を広げられる。
   - 残りが少ない → 本人が続けるほうが効率がよい。ただし、「記録が少ないから任せる」と、本人の負担が増える。本人の意向を先に聞く。
3. **意向**: 直近の `docs/minutes/*.md` の「アクション」「未解決・次回」、議題 Issue と Issue のコメントでの、本人の発言。
4. **負荷**: いま**個別に**持つ open の Issue の数。`gh issue list --assignee <login> --state open --json number,title,assignees` で取り、**担当が 3 人以上いる Issue（議題や決めることのように、全員が担当のもの）は数えない**（全員担当を数えると、全員が同じ件数に見えて、負荷の差を読み違える）。不在の予定（`docs/minutes/` の「お知らせ」、カレンダーの公開部分）。件数で圧をかけない。数字を書くときは、どの Issue を数えたかも添える。
5. **全員の一覧**: `gh api repos/{owner}/{repo}/collaborators --jq '.[].login'`。

## 出す形（Issue のコメント、または質問の「決める人」の下）

候補ごとに、**事実 → 理由 → 見方 → 懸念**の順で書く。事実から見方へ、一足飛びにつながない。間に「なぜそう言えるか」の理由を 1 文入れる。理由が書けないときは、その見方は書かない。**懸念**は、その人が担当したときに見落としやすい点（盲点）を、事実から 1 つ以上挙げる。

```
- 担当（Leading）の候補
   - <候補 1>
      - 事実: <この Issue や関連 Issue へのコメント、PR、発言など。番号か日付を添える>
      - 理由: <その事実から、何が言えるか（事実が示すことだけ。推測を混ぜない）>
      - 見方: <その理由から、この人が担当するとどう進めやすそうか。「〜かもしれません」と書く>
      - 懸念: <この人が担当したときに起きやすい盲点や偏り。事実を添える>
   - <候補 2>
      - 事実 / 理由 / 見方 / 懸念: <同上>
- 始めやすさの観点
   - 事実: <文書が整っている（どの文書か）、手順が具体的（Issue の何が具体的か）、テストの条件が書かれている、など>
   - 見方: <そのため、この領域に初めて関わる人でも始められそう、という可能性。新しく関わる機会としても開かれている>
- 見えていないこと
   - <GitHub の外で進んでいて、記録に出ないものがありうる、など>
```

- 「事実」には、理由や見方を混ぜない。
- 「理由」は、事実から言える範囲に収める。たとえば「依存の強さにコメントした」という事実から言えるのは、「この Issue の設計の論点を、すでに考えている」までで、「判断が速い」とは言えない。
- **懸念の見つけ方**（当てはまるものを、事実つきで書く。無理に作らない）。観点は、次の 6 つ。
  - **過去の量**: 直近 2〜4 週間で、その人が実装・設計・レビュー・マージをどれだけ担ってきたか。`git log --since=<日付>` の作者別の件数と、PR の作者・マージした人で数える。Claude との共作（`Co-Authored-By: Claude`）のコミットは、実装の量には数えない。ただし、指示・確認・マージの手間はかかっているので、別に書く（例: 「54 件のうち 52 件は Claude との共作で、指示と確認の負荷がある」）。
  - **これからの量**: いま個別に持つ Issue、期限が近いマイルストーン（M2・M3）の中で、すでに関わる作業、確認待ちの PR、MTG のアクション。全員担当の Issue は数えない。
  - **将来の予定との重なり**: 担当する期間に、大きな予定や不在がないか。チームのカレンダー（非公開リポジトリ `MouthOfGod_transcripts` の `calendar/upcoming.md`）と、公開の議事録の「お知らせ」から読む。**カレンダーの個人の予定（学会発表・試験・面接・私用など）は、公開の Issue・コメントに書かない。** 書くのは「この期間は、予定が重なっていそうです。本人に確認します」までにして、詳細を書かない。読めないときは「未確認」と書く。
  - **設計を一人で抱えている**: 設計の文書（`docs/`）、型の定義（Core）、レビューが、同じ人に集まっていないか。集まっていると、その人の見落としを外から指摘する人がいない。
  - **疑問を出した人が作る側になる**: 設計に疑問を出した人が実装も担うと、その疑問を外から確かめる人がいなくなる。
  - **新しく関わる機会が減る**: すでに関わりの深い人が続けると、ほかの人が関わる機会が無い。
  - 記録が少ない領域では、**引き継ぎの負担が増える**ことも書く（続けるほど、引き継ぐ人が読むものが増える）。
- 懸念は、人を責める言い方にしない。「この人は多すぎる」ではなく、「量が多いので、これ以上を足してよいか、本人に確認したい」の形にする。
- 引用する発言は、本人の言葉をそのまま（短く）。意訳しない。
- 材料が足りず、候補を挙げられないときは、「始めやすさの観点」だけを書く。推測で人の名前を挙げない。

## 呼び出し元
- `issue-hygiene`: 「担当（Leading）がいない」節の各 Issue に、1 行で「候補はこのスキルで出せます」と添える。候補の一覧は、人が求めたときに出す（毎週、全員の一覧を出さない。圧になるため）。
- `ask-decision`: 質問の「決める人」が決まっていないとき、このスキルの候補を添える。
