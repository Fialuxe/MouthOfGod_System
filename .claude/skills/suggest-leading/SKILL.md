# suggest-leading

> この仕組みを直す前に、[仕組みの前提](../../../docs/automation-premise.md) を読む（補助線であって決まりではない。人の負荷を増やさない。責めない・順位をつけない）。

担当（Leading）がいない Issue に、**候補の一覧**を作る。決めるのは人で、ここで挙げるのは材料だけ。狙いは、**効率を落とさず、かつ誰の可能性も狭めない**こと。

## 守ること（先に読む）
- **1 人を推さない。** 候補は 2〜4 人。順位をつけない。「この人が最適」と書かない。
- **評価の言葉を書かない。** 「コメントが少ない」「やる気がない」のような、人の評価に読める言葉は使わない。書くのは、事実と、そこから言える「この作業との相性」だけ。
- **候補に必ず入れるもの**: (1) これまでの関わりが深い人 (2) 引き継ぎのしやすさから見て、別の人でも担当できる場合の人 (3) **まだこの領域に関わっていない人**（新しく関わる機会。意向が見えるときだけ。見えなければ「立候補を歓迎します」と書く）。
- **本人の意向を最優先する。** 議事録・コメントに「やりたい」「興味がある」「触ってみたい」と書いた人は、候補に入れて、その発言を引く。逆に「手が埋まっている」「不在」と書いた人は、理由を添えて候補から外す、または負荷を明記する。
- **記録が見えない領域は、見えないと書く。** Claude は GitHub の外（手元の Unity、サンドボックスのシーン、ハードウェア、Slack、口頭）が見えない。記録が少ない人を「関わっていない」と決めつけない。`docs/mtg-context.md`「プロジェクトの分野」の注意と同じ。
- **非公開の情報を使わない。** 議事録は `docs/minutes/`（公開）だけを使う。文字起こしの全文（非公開）は使わない。
- 公開リポジトリに書く。人を傷つけうる言い方（比較して下げる、能力を推し量る）をしない。

## 材料（Issue ごとに集める）
1. **関わりの深さ**（事実だけ）: **その Issue と、つながる Issue（親・Blocked by・Blocking）にコメントした人**、その Issue が触る場所（`Assets/Scripts/<機能>`、`docs/`）の `git log` の作者・PR の作者、過去の担当。
   - **注意**: Claude の作業は、代表者（`Fialuxe`）のアカウントで投稿・コミットされる。そのため、コミットの作者だけを数えると、代表者に偏って見える。コミットの作者名が `Claude` のもの、`Co-Authored-By: Claude` のもの、dev-loop の PR は、代表者の実績に数えない。
2. **引き継ぎのしやすさ**: その領域の README・設計書（`docs/architecture.md` など）・コメント・PR の本文の量と、Issue の経緯の残り方。**Issue の「やること」と「できたと言える状態」が具体的か**（手順が書かれているか、テストの条件があるか）も見る。
   - 残っている → 別の人が引き継ぎやすい。担当を広げられる。
   - 残りが少ない → 本人が続けるほうが効率がよい。ただし、「記録が少ないから任せる」と、本人の負担が増える。本人の意向を先に聞く。
3. **意向**: 直近の `docs/minutes/*.md` の「アクション」「未解決・次回」、議題 Issue と Issue のコメントでの、本人の発言。
4. **負荷**: いま Leading を持つ open の Issue の数（`gh issue list --assignee <login> --state open`）。不在の予定（`docs/minutes/` の「お知らせ」、カレンダーの公開部分）。件数で圧をかけない。多い人は、「手が足りているか」を確かめる材料にするだけ。
5. **全員の一覧**: `gh api repos/{owner}/{repo}/collaborators --jq '.[].login'`。

## 出す形（Issue のコメント、または質問の「決める人」の下）

候補ごとに、**事実 → そこから言える効率 → 他の人でもできる理由（可能性を開く）**の順で書く。事実と、そこからの見方を、分けて書く。

```
- 担当（Leading）の候補
   - <候補 1>
      - 事実: <この Issue や関連 Issue へのコメント、PR、発言など。番号か日付を添える>
      - 効率の見方: <その事実から、この人が担当すると効率がよさそうな点>
   - <候補 2>
      - 事実: <同上>
      - 効率の見方: <同上>
- 他の人でもできる理由
   - 事実: <文書が整っている（どの文書か）、手順が具体的（Issue の何が具体的か）、テストの条件が書かれている、など>
   - 見方: <そのため、この領域に初めて関わる人でも進められそう、という可能性>
- 見えていないこと
   - <GitHub の外で進んでいて、記録に出ないものがありうる、など>
- 決め方
   - <立候補、MTG で相談、のどれかを案として 1 行。誰かに押しつけない>
```

- 「事実」には、見方や評価を混ぜない。「効率の見方」と「他の人でもできる理由」は、推測として書く（「〜かもしれません」「〜と思われます」）。
- 引用する発言は、本人の言葉をそのまま（短く）。意訳しない。
- 材料が足りず、候補を挙げられないときは、「他の人でもできる理由」だけを書いて、「立候補を募ります」と添える。推測で人の名前を挙げない。

## 呼び出し元
- `issue-hygiene`: 「担当（Leading）がいない」節の各 Issue に、1 行で「候補はこのスキルで出せます」と添える。候補の一覧は、人が求めたときに出す（毎週、全員の一覧を出さない。圧になるため）。
- `ask-decision`: 質問の「決める人」が決まっていないとき、このスキルの候補を添える。
