# ask-decision

> この仕組みを直す前に、[仕組みの前提](../../../docs/automation-premise.md) を読む。

進めない理由を、その場にいなかった人が一度読んで分かるように書く。質問は、それが関わる Issue か PR に、コメントで 1 件だけ書く。同じ Issue に、答えの無い `<!-- claude-question -->` がすでにあれば書かない。

状況が分からないだけなら、このスキルではなく `docs/mtg-context.md`「Claude からの質問」の「状況を聞く」形を使う。このスキルは、状況は分かっていて、選ぶことだけが残っているときに使う。

## 書く前に、先に整理する
- `docs/question-lessons.md` を読み、過去に通じなかった型を避ける
- 質問の中で使う言葉・番号・前提を、全部挙げる（下書きの後に読み手が確かめるが、先に自分で挙げておく）。読む人がその場で分からないものは、質問の中に 1 文で添える（書き手に当たり前のことほど、抜けやすい）
- 何を作ろうとして止まったか（実装の名前と、その働き）
- 決まっていないことは何か（1 つに絞る）
- 選択肢ごとに、進めた後で何が起きるか
- 決めないままだと、どの段階で何に困るか
- 今の時点で、何が絞れていないか（どんな可能性が残っているか）

## 投稿する前に、前提を知らない目で読ませる

下書きができたら、投稿する前に、一時ファイルに書き、`python3 .claude/skills/cold-read/cold_read.py <ファイル>` で読ませる。渡すのは**下書きの本文だけ**（Issue や会話の文脈を添えない）。このスクリプトは、`claude -p` を指示文を短くしてツールを外し、軽く起動する（サブエージェントで呼ぶと、親の長い指示文とツールの定義が付いて、1 回あたり約 39,000 トークン多くかかる）。指示の本文は `.claude/agents/cold-reader.md`。チームの一員で、コードと対象の Issue を読んでいない人に読ませる、というのが狙い。書き手には当たり前のことが抜けるので、書き手の自己点検だけでは見つからない。

1. 読み手が挙げた「分からない所」を、質問の中で説明する（言葉の説明を 1 文足す、指す先を書く、足りない情報を書く）
2. 直した下書きを、もう一度読ませる。「分からない所はありません」になるまで繰り返す（最大 3 回。それでも残るものは、質問の「決めないと困ること」に「未整理」として書く）
3. 通ったら投稿する

## 本文の形

各項目は、**項目名だけの行**の下に、字下げした箇条書きで本文を書く。項目名と本文を、同じ行に続けて書かない。選択肢は、さらに 1 段下げる。

```
**Claude からの質問**: <決めてほしいことを 1 文で。「〜を入れますか？」の形>

- どこから
   - <どこで止まったか。例: 開発（dev-loop）の PM が止まりました。>
- 何をやっている時に止まったか
   - <「◯の実装にあたり、この機能は◻︎するものです。ここを考える上で、〜するか〜するかが分かりませんでした。」の形で、簡潔に>
   - <「仕様どおり」で進められる部分は、具体的に列挙する>
   - <その仕様が決まった日（mm/dd）。その後に関連する変更があれば、変更を説明する。なければ「変更は見つかりませんでした」と書く。日付が分からなければ「未確認」と書く>
   - <変更を踏まえて、その実装のまま進めて良さそうか>
- <土台の名前>とは（例: Core とは。話に出す土台がある時だけ。下の「書き方」を見る）
   - <その土台が何のためにあるか。今ある機能を 2〜4 個。足そうとしている機能が、今は無いこと>
- 何の話か
   - <この機能が何をするものか。使う名前（クラス名など）は、まず言葉で働きを書き、名前は添える程度にする>
- 判断の大きな分かれ目
   - <判断の根にある問い。例: 「そもそも保存するのか」。どの答えなら、どの選択肢に進むか>
- 選択肢
   - A. <案。進めた後に起きること>
   - B. <案。進めた後に起きること>
   - C. <あれば。無理に作らない>
- なぜ今決めるか
   - <待っている Issue。番号を 1 行ずつ並べる>
- 決めないと困ること
   - <どの段階で、何に困るか>
   - <今は何が絞れていないか。決まると、どんな可能性が絞れるか>
- 一番良さそうな案
   - <案の記号と、その理由>
- 決める人
   - <担当。いなければ「決める人を決めるところからお願いします」と書く>
   - <決まらなければ、どの案で進めるか>

答えは、このコメントへの返信（コメント）か、MTG で。「A でいい」だけで足ります。
<!-- claude-question -->

---
_Generated by [Claude Code](https://claude.ai/code)_
```

## 書き方
- 日本語は「です・ます」で書く。1 文は 40 字ほどまで。
- 「Core に足す」のように、土台の名前を出す時は、読む人がその土台を知らない前提で補足する。土台が何のためにあるかを 1 文で書き、今ある機能を数個挙げ、足そうとしているものが今は無いことを書く。今ある機能は、土台の README や `docs/architecture.md` で確かめて書く。
- 「仕様どおりに進めます」「いつもの手順で進めます」のように、指すものを省かない。読む人が上にスクロールし直さなくてよいように、何をどう進めるかを具体的に書く（例: 「Issue に書かれた 4 つのことは、そのまま作れます。1 つ目は…」）。
- 「決めないと困ること」には、段階を名指しする（例: 「チュートリアル 3 を作る時」）。「後で困ります」のような書き方にしない。
- 見えていないことを、推測で埋めない。推測は「推測ですが」と書く。
- 一番良さそうな案は、必ず 1 つ選び、理由を書く。選べない時は、何が分かれば選べるかを書く。
- 公開リポジトリなので、トークンや個人情報を書かない。
- 書いたら、`docs/mtg-context.md`「Claude からの質問」の約束（最後の行の目印、1 コメント 1 質問）に合っているか確かめる。
- 人が「わからなかった」と書いた、または質問を飛ばして話したのを見つけたら、`docs/question-lessons.md` に 1 件足す（週次の `issue-hygiene` も探して足す）。
